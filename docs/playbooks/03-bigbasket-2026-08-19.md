## 1. Availability semantics across all four platforms

This is the table that matters for any cross-platform inventory panel.

| | Blinkit | Swiggy Instamart | Zepto | BigBasket |
|---|---|---|---|---|
| Integer stock exposed | **Yes** | No | **Yes** | **No** |
| Authoritative field | `inventory` (int) | `variations[].inventory.inStock` (bool) | `availableQuantity` (int) | `availability.avail_status` (enum) |
| Value space | 0..n | true / false | 0..n | `"001"` in stock, `"000"` out |
| Field that lies | `is_sold_out`, false on every row | none observed | `availableQuantity` and `outOfStock` **in the DOM** | `inv_info.skus[].qty`, `1` on every row |
| Where to read stock | hydrated Redux store | SSR `___INITIAL_STATE___` | **raw XHR before hydration** | listing-svc JSON |
| Is hydrated state safe | Yes | Yes | **No, poisoned by `always_in_stock`** | N/A, search never hydrates state |
| Low-stock hint | infer from int | `inventory.lowStockText` | infer from int | none |
| Per-order cap | `max_count`, mirrors `inventory` | `cartAllowedQuantity.allowedQuantity` | `productVariant.maxAllowedQuantity` | `sku_max_quantity`, `0` means uncapped |
| Demand proxy | none | none | none | `number_of_skus_sold`, bucketed string |
| Out-of-stock presentation | badge on card | unverified | normal card, live ADD, **no badge** | "Out Of Stock" overlay plus "Notify Me" button |
| Price unit | rupee string with symbol | units plus nanos | **paise integer** | rupee string, no symbol |

**The load-bearing conclusion.** Only Blinkit and Zepto give you a stock depth number. Swiggy gives a boolean plus a soft low-stock string. BigBasket gives a two-state enum and nothing else. Do not design a unified schema with a mandatory numeric `qty` column. Model availability as an enum with an optional depth, and let BigBasket rows carry a null depth rather than a fabricated zero or one.

Each platform hides its truth in a different place, and three of the four ship a decoy field that a reasonable engineer would reach for first. There is no shared rule. Every platform needs its own availability resolver.

## 3. Location flow

1. Load `www.bigbasket.com`. Dismiss the app banner and any "Got it" tooltip.
2. Click the header delivery selector. Before location it reads a prompt; after, it reads `Delivery in 6 mins  700048, Kolkata`.
3. Type the pincode into the location input. Suggestions render.

   **UNVERIFIED:** the suggestion list text and shape were never captured in this run. The agent's step 2 output did not reach stdout. Capture and log the raw suggestion strings on your first local run before writing a matcher. Given Blinkit duplicated its suggestion text and Swiggy served a Madhya Pradesh option for 700048, assume BigBasket has its own trap and match on substring plus expected city, never index 0.

4. Select the Kolkata / West Bengal suggestion. In this run the location applied without a separate map confirm click.
5. Assert the header before trusting anything downstream.

### 3.1 The guard, and the field that is not the guard

`_bb_locSrc` stayed `default` **after** the pincode was successfully applied. It is not a location-source guard and it is not the analogue of Swiggy's `locationSource: swgyUL`. Do not gate on it.

Guard on all three of:

- cookie `_bb_pin_code == "700048"`
- header text contains the pincode
- every product row's `visibility.sa_id == 28232`

The third is the strongest, because it is per-row and travels with the data rather than with the session.

### 3.2 The area label is junk

`_bb_addressinfo` base64-decodes to:

```
22.6015112|88.4003915|Kasba|700048|Kolkata|1|false|true|true|Bigbasketeer
```

Fields: lat, lon, area, pincode, city, ?, ?, ?, ?, membership tier.

The area reads **Kasba**, which is south Kolkata at roughly 22.51 lat. The lat/lon in the same cookie is 22.60, which is the Dum Dum side. The Snowplow beacons repeat it as `Location: "Kolkata|Kasba"`. The label is a stale default and does not track the pincode. Never assert on it, never store it as the resolved area.

## 4. API surface

### 4.1 The one that matters

```
GET /listing-svc/v2/products?type=ps&slug=Mango&page=1&bucket_id=52
```

HTTP 200, ~324 KB JSON, 20 products per page. Works with the location cookie jar attached. No JS execution needed after bootstrap.

`bucket_id=52` was present on the live call. Purpose unknown, stable across the Mango and Onion calls in the same session. Carry it through, do not invent values.

│       └── bread_crumbs
├── screen_info
├── base_img_url
├── analytics_attrs

├── widget_details

**Log `is_llm_flow` and `is_llm_timeout` on every pull.** BigBasket has an LLM-mediated search path on the envelope. If it engages, ranking is not guaranteed reproducible between two pulls of the same query, and a timeout may silently degrade you to a different ranker. This is the only platform of the four with an observable non-deterministic ranking switch. Store both flags as columns on the pull, not just the rows.

## 5. Product schema

### 5.1 Identity

| Field | Type | Note |
|---|---|---|
| `id` | **string** | the SKU id |
| `requested_sku_id` | string | equals `id` on all sampled rows |
| `ean_code` | string | equalled `id` on the sampled row, do not assume it is a real EAN |
| `absolute_url` | string | `/pd/<id>/<slug>/` |
| `parent_info.parent_id` | **int** | parent SKU, groups variants |
| `parent_info.child_id` | **int** | equals `id` |
| `inv_info.skus[].id` | **int** | equals `id` |
| `rating_info.sku_id` | **int** | **the parent, not this row.** `10000588` on a row whose `id` is `10000587` |

Same logical entity arrives as string in one place and int in three others, and `rating_info.sku_id` is a different entity entirely. Type the id column as text, cast on ingest, and do not join on `rating_info.sku_id`.

### 5.2 Availability

| Field | Value on 20 sampled rows |
|---|---|
| `availability.avail_status` | `"001"` on 18, `"000"` on 2 |
| `availability.button` | `"Add"` / `"Notify Me"` |
| `availability.label` | absent / `"Coming back soon"` |
| `availability.not_for_sale` | false on all 20 |
| `availability.display_mrp`, `display_sp` | true on all 20 |
| `availability.show_express` | false on all 20 |
| `sku_max_quantity` | `0` on all 20 |
| `inv_info.skus[].qty` | **`1` on all 20, including both out-of-stock rows** |

Resolver: `in_stock = (avail_status == "001")`. Treat `button` and `label` as display strings only.

### 5.3 The inv_info trap

`inv_info.skus[]` looks like the inventory field and is not.

Proven not stock: it reads `1` on `fresho! Chausa Mango` and `Candyman Tadka Lollipops`, both of which are `avail_status: "000"` and render an Out Of Stock overlay. A stock field cannot read 1 on an out-of-stock row.

Most likely a bill-of-materials multiplier: how many physical SKUs compose one sellable listing, which is 1 for every non-combo row. A combo should show more than one entry in the array. **This reading is unconfirmed.** All 20 rows had zero variance, so the BOM interpretation cannot be distinguished from a hardcoded constant on this sample. Test it against a row where `combo` is non-null before relying on the interpretation. What is certain is only the negative: it is not stock.

Similarly `sku_max_quantity: 0` means no per-order cap, not zero stock. Two fields that both read like inventory, neither of which is.

And `pricing.discount.camp_detail` carries `on_inv_v_f`, `off_inv_v_f`, `on_inv_c_f`, `off_inv_c_f`, `on_inv_m_f`, `off_inv_m_f`. The `inv` there is **invoice**, not inventory. Vendor, company and manufacturer funding splits on the discount. Easy to grep into by mistake.

### 5.4 Pricing

| Field | Note |
|---|---|
| `pricing.discount.prim_price.sp` | selling price, **string**, no symbol, e.g. `"74.25"` |
| `pricing.discount.prim_price.rsp` | reference selling price |
| `pricing.discount.mrp` | **string** |
| `pricing.discount.d_text` | badge text, `"21% OFF"` or `"₹12 OFF"`, two different formats |
| `pricing.discount.d_avail` | **string** `"true"`, not a boolean |
| `pricing.discount.prim_price.base_price` / `base_unit` | unit-normalised price, e.g. `12.8` per `100g`. Free normalisation, use it |
| `pricing.discount.subscription_price` | |
| `pricing.discount.sec_price` | null on all sampled rows |
| `pricing.discount.deal_score` | float, 0.14 to 0.17 observed |

Prices are rupee strings, not paise. This is the inverse of Zepto. If you share a parser across platforms, the unit conversion must be per-platform and explicit.

`d_avail` and `offer_available` are string `"true"`, not booleans. Truthiness on the raw value will pass for the string `"false"` too.

### 5.5 Everything else worth keeping

| Field | Note |
|---|---|
| `desc` | product name **without** brand. Concatenate with `brand.name` for a display name |
| `brand.{name,slug,url}` | note trailing spaces on some names, `"Epigamia "`, `"Max Health "` |
| `w` | display pack, `"500 g"`, `"1.75 L"`, `"8 pcs"` |
| `magnitude` + `unit` | structured pack, `"500"` + `"g"` |
| `pack_desc` | container, `"Cup"`, `"Jar"`, `"PET Bottle"`, often empty |
| `category.{tlc,mlc,llc}_name/_slug/_id` | three-level taxonomy. `llc_slug` is a query fragment `type=pc&slug=mangoes`, not a path |
| `number_of_skus_sold` | `"32K+ sold (1 mo)"`. Bucketed string. Parse prefix and multiplier separately |
| `rating_info.{avg_rating,rating_count,review_count}` | null on some rows |
| `visibility.{path_id,fc_id,sa_id,supply_chain_ecs}` | per-row store binding, use as the assertion |
| `children[]`, `variant_info[]`, `combo`, `bxgy` | empty or null on all 20 sampled rows |
| `variable_weight.{msg,link}` | present on fresh produce |
| `images[]` | five sizes each, `s/m/l/xl/xxl`, host `bbassets.com` |
| `video_links[]`, `gif_links[]` | present on some fresh SKUs |
| `prescription_only`, `is_tobacco`, `is_free_reward`, `quality_report.enabled` | flags |

## 6. BigBasket gotchas

1. **No integer inventory exists anywhere in the listing payload.** Confirmed by inspection of the full flattened key set. If a stock depth column is required, BigBasket cannot fill it.
2. **`__NEXT_DATA__` on `/ps/?q=<query>` holds the homepage payload**, not search. It is populated with `custPageData`, My Smart Basket, Banana Robusta. A parser that reaches for `__NEXT_DATA__` returns plausible product rows that have nothing to do with the query, with no error. This is the same class of silent failure as the Swiggy and Zepto Bengaluru default, and quieter, because the rows are real products from the correct store.
3. `_bb_locSrc` does not flip when the pincode is set. Not a guard.
4. `_bb_addressinfo` area label does not track the pincode. Not a guard.
5. Id type inconsistency across four fields, plus `rating_info.sku_id` pointing at the parent.
6. `d_avail` and `offer_available` are strings, not booleans.
7. `d_text` mixes percent and rupee formats in the same column.
8. Brand names carry trailing whitespace. Strip on ingest or your brand dimension will split.
9. `is_llm_flow` means ranking may not be reproducible run to run.
10. Search expands `mango` to `aam`, pulling in Aam Doi, Aam Kasundi, Aam Panna and Kaccha Aam. Only 2 of the top 20 are actual mangoes. This is synonym expansion, distinct from Zepto's semantic drift, which pulled in a lychee yogurt containing no mango token at all. Both need a keyword filter, but the filters are not the same filter: a BigBasket filter must know the vernacular synonym set.

## 9. Firecrawl operating notes, updated

Contradicting the earlier sessions: this run acquired a session on the **first attempt** and held it across three resumes for 9m18s. The 9-to-3 failure ratio from the Blinkit and Swiggy sessions is not a fixed property. Treat acquisition as variable, keep the retry with backoff, but do not budget as though failure is the default.

Confirmed again:

- `scrapeOptions` must be a real JSON object. A single-quoted dict literal fails schema validation with `expected object, received string`.
- Resume via `scrapeId` is much cheaper than re-bootstrapping the location flow. All three follow-ups here used it.
- Large results spill to `/mnt/user-data/tool_results/*.json`. Unpack: load file, index `[0]`, parse the `text` field as JSON, then read `output`, `stdout` or `result`.
- Long multi-part agent prompts truncate. The first prompt here asked for six labelled outputs and only reached the third before the narrative ran out. Split into short targeted calls on a resumed session rather than one long instruction list.
- Asking the agent to run a single expression and print the raw string verbatim is far more reliable than asking it to extract and summarise.
